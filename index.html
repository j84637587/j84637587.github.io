OPC UA學習

因為本人最近在求職，對於相關工業協定有興趣，所以整理了一些筆記，方便自己複習，也希望對其他人有幫助。

OPC UA 是什麼?

OPC UA 的全名是 Open Platform Communications Unified Architecture。

他與前幾篇 Modbus、DNP3 一樣都是工業通訊協定，所以他也是會去定義說要如何交換資料，比如：

  • 目前有哪些設備？
  • 這台設備有哪些資料可以讀取？
  • 這筆資料是否有效？是什麼時間量測的？
  • 溫度發生變化時請主動通知我
  • 請呼叫這台馬達的啟動或停止功能

OPC UA 主要應用的產業有：智慧製造、PLC、SCADA、MES、ERP、雲端

這裡也再次補充以下：

  • Modbus 主要應用產業：PLC、感測器、工廠設備
  • DNP3 主要應用產業：電力、變電站、SCADA

那麼 OPC UA 跟 Modbus、DNP3 有什麼不同呢?

以讀取溫度為例：

  • Modbus:

    • 讀取 Holding Register 40001 -> 回傳 752
    • 但必須查手冊才知道是 75.2 °C ， 單位由手冊定義。

  • DNP3:

    • 讀取 Analog Input Point 5 -> 回傳數值 75.2、時間戳記與品質狀態
    • 但通常仍需 Point List(手冊) 才知道 Point 5 是馬達溫度。

所以以上兩者都很依靠預先定義。

OPC UA 則是會去定義一個「物件模型」，也就是說它會把設備、資料、功能都抽象成「物件」與「屬性」，並且提供一個標準化的方式去描述這些物件。

  • OPC UA:
    • 讀取 Motor1.Temperature -> 回傳數值 75.2、單位 °C、時間戳記與品質狀態
    • 這裡 Motor1 是一個物件，Temperature 是它的屬性，這個屬性會包含數值、單位、時間戳記與品質狀態。

從上面的例子可以觀察出來，OPC UA存取資料的方式非常像物件導向程式設計的概念，讓設備與資料的描述更直覺、更容易理解!!

並且 OPC UA 不只交換數值，也交換數值的意義。就比如上面的例子。

傳輸方式

通常 OPC UA 會使用 TCP 傳輸，因為傳統架構是以 Client/Server 為主。

但在比較新的 Pub/Sub 架構中，則會使用 UDP 或 MQTT 來傳輸。

  • 說到 Pub/Sub 架構，剛好可以回顧 DNP3 也會使用 Pub/Sub 架構，所以 DNP3 也會使用 UDP 或 MQTT 來傳輸。

Pub/Sub 架構是甚麼？

Pub/Sub；Publish-Subscribe 是一種一對多的通訊模式，通常會有三個角色：

  1. Publisher：發布者，負責產生資料並發布出去。
  2. Subscriber：訂閱者，負責接收資料。
  3. Broker：中介者，負責管理訂閱關係，將 Publisher 發布的資料轉發給所有訂閱者。

為甚麼要用 Pub/Sub 架構？

可以假設在 TCP Client/Server 架構中，Client 端必須不斷地去詢問 Server 端：「你現在溫度多少？」。

可能一秒問10次，甚至更多，這種做法在設備變多時，網路很快就會塞車。

所以就轉念一想，如果能讓感測器自己決定「什麼時候要發布資料」，而不是由 Client 端一直去詢問，那就可以大幅減少網路流量。

所以就使用 Pub/Sub 架構，並設定「當溫度改變超過 0.5 度時才發布」。

而中控電腦、手機 App、歷史資料庫都去「訂閱」這個溫度感測器。平時網路很安靜，一旦溫度一變，所有人同時、即時收到最新數據，甚至警告。

為什麼 Pub/Sub 架構會使用 UDP 或 MQTT？

  1. 一對多: TCP 是一對一的連線，Pub/Sub 架構需要一對多的通訊模式，所以 TCP 並不適合。TCP 要一對多會增加系統的複雜度，因為要維護多個連線，還要處理每個連線的狀態。
  2. 低延遲: UDP 是無連線的協定，傳輸延遲低，適合即時性要求高的應用。MQTT 是基於 TCP 的輕量級協定，設計上也考慮了低延遲的需求，並且提供了 QoS 等級來平衡可靠性與延遲。
  3. 資料特性，在工業上感測器通常是低延遲發送的，例如溫度感測器可能每5ms就發送一次資料，頻率非常高，因此就算丟失一個封包，下個5ms就會補上了。但 TCP 卻會補送，這時候資料早就過期了。

OPC UA 資料形式?

OPC UA 不只是「讀一個值」，它的核心是 Information Model。

Information Model 是一種資料結構，用來描述設備、資料、功能之間的關係。它將設備抽象成物件，物件有屬性、方法和事件。

簡單來說 Information Model 就是常見的物件導向程式設計的概念，物件有屬性、方法和事件。

所以 OPC UA 相比於 Modbus、DNP3，提供了更豐富的資料結構與語意，讓設備與資料的描述更直覺、更容易理解。還省去了手冊查詢的麻煩，因為資料本身就包含了意義。但同時也增加了實作的複雜度，因為需要處理更多的資料結構與語意。

安全性?

OPC UA 在 Client/Server 中使用 TCP 傳輸，TCP 本身具有可靠性、與基礎的安全性。但在 Pub/Sub 架構中，使用 UDP 或 MQTT 傳輸，這些協定本身並不具備安全性。

OPC UA 要怎麼在 Pub/Sub 架構中確保資料的安全性呢？

首先是 TCP 雖然具備可靠、與基礎的安全性，但資料本身是沒有加密的，所以仍然有隱患。而 UDP、MQTT 更是如此。

所以 OPC UA 會對訊息訊息去做簽章與加密，確保資料的完整性與安全性。

簽章是什麼?

加密這個很常聽到，就是利用演算法去把資料轉換成一個只有特定人才能解讀的形式，確保資料不被竊取。

其中又可以分成對稱式加密與非對稱式加密。 (這部分在此不多做說明)

那簽章呢? 假設 Client 某次傳送給 Server 說 “我要修改馬達轉速到100rpm”，這筆資料可能會被加密成 “0xA1B2C3D4”。

但如果有人竊取了這筆資料，加密可以防止攻擊者直接看懂內容，但不能單獨證明這筆資料是否真的由合法 Client 發送，也不能確認資料在傳送途中是否遭到修改。

因此簽章就是為了解決這個問題，簽章會在資料中加入一個「簽名」，這個簽名是由 Client 的私鑰產生的，Server 可以用 Client 的公鑰去驗證這個簽名是否正確。

Client 會根據訊息內容計算摘要，再使用自己的私鑰產生簽章，並將訊息與簽章一起傳送給 Server：

Server 收到後，可以使用 Client 的公鑰驗證簽章。

如果簽章驗證成功，代表：

  • 訊息是由持有 Client 私鑰的一方簽署的。
  • 訊息內容在傳送途中沒有被修改。

假設攻擊者將指令修改為：我要修改馬達轉速到10000rpm

由於訊息內容已經改變，原本的簽章便無法通過驗證。攻擊者沒有 Client 的私鑰，也無法替修改後的訊息產生合法簽章。

不過，簽章本身不能防止重送攻擊。

假設攻擊者完整攔截一筆合法訊息，之後將完全相同的訊息與簽章再次傳送給 Server。因為內容沒有被修改，所以簽章仍然可能驗證成功。

DNP3學習

因為本人最近在求職，對於相關工業協定有興趣，所以整理了一些筆記，方便自己複習，也希望對其他人有幫助。

DNP3 是什麼?

DNP3 的全名是 Distributed Network Protocol 3。

它主要被使用在以下場景：

  • 電力系統
  • 變電站自動化
  • 遠端終端設備 RTU
  • SCADA 監控系統

簡單來說，DNP3 就是一套專門給工業控制與電力監控使用的通訊協定，讓控制中心可以和遠端設備穩定交換資料。

它和 Modbus 一樣都屬於應用層協定，但 DNP3 在設計上更強調：

  • 不穩定通訊環境下的可靠傳輸
  • 事件回報
  • 時間戳記
  • 多層資料模型

例如控制中心會問：

  • 現在開關是不是跳脫了?
  • 目前量測到的電壓是多少?
  • 某個警報是什麼時間發生的?
  • 請你幫我把某個輸出接點打開

所以在需要監控大量遠端設備，而且還很在意事件先後順序的情境下，DNP3 通常會比 Modbus 更常被拿來使用。

這也表示 Modbus 主要是在取得即時性資料，而 DNP3 則是更偏向「事件導向、狀態變化紀錄與回報」的資料傳輸。

DNP3 資料形式?

DNP3 本質上是 Object-based protocol，線上傳輸的資料會用 Group + Variation 指定「這是什麼資料、用什麼格式編碼」。

DNP3 根據用途、型態會分以下：

用途：

  1. Static Data：靜態資料，例如開關狀態、量測值
  2. Event Data：事件資料，例如開關跳脫、警報觸發

型態(Object) 有很多這裡不一一列出：

  1. Binary Input / Output：二進位輸入/輸出，例如開關、繼電器
  2. Analog Input / Output：類比輸入/輸出，例如電壓、
  3. Counter：計數器，例如累計脈衝數、累計事件數
  4. Control：控制命令，例如開關操作、設定值變更

為什麼 DNP3 很重視事件?

很多工控場景不只是想知道「現在值是多少」，而是更在意：

  • 什麼時候變了?
  • 哪個點先變?
  • 有沒有漏掉重要警報?

因此 DNP3 內建了 event-oriented 的概念。

例如某個開關在 10:01:05 跳脫，另一個警報在 10:01:07 發生，那系統除了知道最後狀態，也能根據時間戳記了解事件順序。

這對電力系統非常重要，因為故障分析常常就是在追查：

  • 是哪個保護先動作?
  • 是哪個斷路器先跳?
  • 是故障造成警報，還是警報觸發了後續動作?

Class 0 / 1 / 2 / 3 是什麼?

DNP3 會把資料或事件分成不同類別，最常見的是：

  • Class 0：目前靜態資料
  • Class 1：高優先事件
  • Class 2：中優先事件
  • Class 3：低優先事件

這樣 Master 就能依照需求安排輪詢策略。

例如：

  • 平常先頻繁讀取 Class 1 事件
  • 其次讀取 Class 2、Class 3
  • 偶爾再做一次 Class 0 完整掃描

這種方式比「每次都把所有資料全部重讀」更有效率，也更適合頻寬有限的環境。

DNP3 可以跑在哪些傳輸方式上?

DNP3 本身是應用層協定，底層可以跑在不同媒介上，常見的是：

  • Serial
  • TCP/IP

所以你會看到：

  • DNP3 Serial
  • DNP3 over TCP

如果走 TCP/IP，概念上就像：

Layer Protocol
7 DNP3
4 TCP
3 IP
2 Ethernet

但如果走 Serial，就會搭配串列傳輸的資料鏈路層格式。

DNP3 跟 Modbus 差在哪?

參考以下表：

比較項目 Modbus DNP3
常見場景 一般工業設備通訊 電力、SCADA、遠端監控
資料抽象 偏寄存器導向 偏物件導向
事件機制 較弱 很強
時間戳記 通常需額外設計 原生支援較完整
適合環境 簡單、直接 複雜、遠端、需高可靠性

所以你可以粗略理解成：

  • Modbus 比較像「我要去讀某個位址的資料」
  • DNP3 比較像「我要取得某種類型的設備狀態與事件」

兩者都很常見，只是適合的應用情境不太一樣。

Unsolicited Response 是什麼?

一般協定常常是 Master 問了，設備才回。

但 DNP3 支援 Unsolicited Response，意思是 Outstation 在特定事件發生時，可以主動送資料給 Master，而不必等主站先問。

例如：

  • 某個保護裝置跳脫
  • 某個重要警報被觸發
  • 某個類比值超過門檻

這樣的好處是反應更快，也能減少主站一直高頻率輪詢所有點位的負擔。

為什麼設備可以主動通訊？

這是因為通訊仍然是用 Serial 或 TCP/IP 的連線，這些連線本身就是可以雙向傳輸的。

時間同步為什麼重要?

既然 DNP3 很重視事件順序，那時間同步就很重要。

如果不同設備的時間不一致，就可能出現：

  • 事件先後順序判斷錯誤
  • 故障分析困難
  • 歷史紀錄失真

因此在實務上，DNP3 系統常常會搭配時間同步機制，讓 Outstation 回報的事件時間盡量準確。

Secure Authentication 是什麼?

早期工業協定很多都不是以資安為主要出發點，DNP3 也一樣。

因此後來延伸出 DNP3 Secure Authentication，目的是避免未授權控制命令被任意偽造或重放。

這代表如果系統要上線到更大範圍網路，甚至跨站點傳輸，就不能只看功能有沒有通，還要考慮：

  • 身分驗證
  • 命令完整性
  • 重放攻擊防護

也就是說，工控協定不能只看「能不能收發資料」，還要看「是不是安全地收發資料」。

感覺 DNP3 比 Modbus 複雜很多? 為什麼部全部更換成 DNP3?

這是因為 DNP3 和 Modbus 本來就服務不同層級與需求。
對只需要簡單 current-state polling 的設備來說，Modbus 的低複雜度反而是優點；DNP3 的 Event、Timestamp、Quality、Buffer 等能力主要在遠端 SCADA 與高可靠度監控環境才真正有價值。
因此實務上常見的不是 DNP3 取代 Modbus，而是 Gateway 同時整合兩者。

Modbus學習

因為本人最近在求職，對於相關工業協定有興趣，所以整理了一些筆記，方便自己複習，也希望對其他人有幫助。

Modbus 到底是什麼?

簡單來講，他就是一套工業通訊協定，主要用於工業自動化系統中設備之間的資料傳輸。

他最主要工作是去定義說：

  • 我要讀哪個設備的哪一筆資料?
  • 我要寫哪個暫存器?
  • 這個命令代表什麼?

例如： Client/Master 端想要讀取 Server/Slave 端的溫度值，他會發送一個讀取命令，指定要讀取的暫存器地址。

  • Client/Master 要怎麼知道要讀取的暫存器地址是什麼? 這就要看設備的規格書，通常會有一個表格列出每個暫存器的功能與地址。

所以這個協定就是在規定

  • 我要做什麼?
  • 讀哪裡?
  • 讀多少?
  • 寫什麼?

所以這樣看來 Modbus 其實是走在 Layer 7 的應用層協定，主要是定義資料的格式與傳輸方式。就好比 HTTP, FTP, DNS 這些協定一樣，都是在應用層去定義資料的格式與傳輸方式。

Modbus 資料形式?

Modbus 最常看到四種資料，稱作功能碼，可以當作遊戲中的 Op Code。

功能碼 類型 名稱 讀寫 資料大小
0x01 Coil 線圈 Read / Write 1 bit
0x02 Discrete Input 離散輸入 Read Only 1 bit
0x03 Input Register 輸入暫存器 Read Only 16 bit
0x04 Holding Register 保持暫存器 Read / Write 16 bit

假設有一個機器，它包含馬達、按鈕開關、溫度感測器。
根據資料可以得出以下的表。

類型 功能 數值
Coil 馬達啟動/停止 0/1
Discrete Input 按鈕開關狀態 0/1
Input Register 溫度感測器數值 16 bit 整數
Holding Register 馬達轉速設定值 16 bit 整數

所以像是 “Read Holding Registers”(這只是示意) 這個命令意思就是 “我要讀取設備裡的一組 16-bit Holding Register”。

Client / Master 怎麼知道要讀哪個暫存器？

通常 Client / Master 端會依據設備的規格書來決定要讀取哪個暫存器。規格書會列出每個暫存器的地址、功能以及資料類型。而規格書稱作 “Modbus Register Map”。

所以 Modbus 協定本身並不會告訴你要讀哪個暫存器，這是由設備的設計者決定的。

Modbus RTU/ASCII/TCP/UDP 是甚麼?

Modbus 常常不會單獨出現會看到 Modbus RTU、Modbus ASCII、Modbus TCP 這些名詞。

剛才有提到 Modbus 是 Layer 7 的應用層協定，因此這邊的 RTU、ASCII、TCP 其實是 Layer 2/3/4 的傳輸層協定。

Modbus RTU(Remote Terminal Unit)

Modbus RTU 是 Modbus 的一種傳輸方式，使用二進位格式傳輸資料，通常用於串列通訊（RS-232、RS-485）。

RS-232 電腦主機就看得到，在舊版的螢幕會使用的 Com Port (主要用來快速傳輸大量資料)。
RS-485 相較 RS-232 更適合長距離傳輸，且可以 1vN 通訊。

封包結構長這樣：

  • Address：設備地址，1 byte，範圍 0~247
  • Function Code：功能碼，1 byte，範圍 1~255
  • Data：資料，長度不固定，依功能碼而定
  • CRC：循環冗餘檢查，2 byte，用來檢查資料是否正確
Address Function Code Data CRC
1 Byte 1 Byte n 2 Byte

你可以注意到 Address 只有 1 byte，範圍 0~247。

但在 Register 中，地址通常是 16 bit，例如 40001。所以實際傳送的 Address 會是 zero-based offset，也就是從 0 開始計數。

則假設要讀取 40001，實際傳送的 Address 會是 0x0000。

但實際上還是要根據設備文件決定。不一定是上面這樣對應。

Modbus ASCII

Modbus ASCII 是 Modbus 的另一種傳輸方式，使用 ASCII 字元格式傳輸資料，通常用於串列通訊（RS-232、RS-485）。

所以 Modbus ASCII 跟 Modbus RTU 很像，最大的不同就是資料傳輸的格式不同，ASCII 是用文字表示，RTU 是用二進位表示。

阿想當然 String vs Binary 資料量差距很大，所以 Modbus ASCII 的傳輸效率會比 Modbus RTU 低很多。

Modbus TCP(Transmission Control Protocol)

Modbus TCP 是 Modbus 的一種傳輸方式，使用 TCP/IP 協定在網路上傳輸資料，通常用於以太網通訊。

所以注意這裡的 Modbus TCP = Modbus + TCP/IP。

所以完整分層會是這樣：

走的是網路協議。

Layer Protocol
7 Modbus
4 TCP
3 IP
2 Ethernet

所以前面的 “Read Holding Registers” 在這邊，其實只是把 Modbus 的資料包裝在 TCP/IP 的封包裡面傳輸。

Modbus Request -> TCP -> TCP Segment -> IP -> IP Packet -> Ethernet Frame -> Ethernet

封包結構長這樣：

  • Transaction Identifier：交易識別碼，2 byte，用來識別請求與回應的對應關係
  • Function Code：功能碼，1 byte，範圍 1~255
  • Data：資料，長度不固定，依功能碼而定
MBAP Header Function Code Data
7 Bytes 1 Byte n

與 RTU 的差別在於：

  1. 沒有 Address，因為 TCP/IP 已經有 IP Address 了
  2. 多了 MBAP Header，用來識別請求與回應的對應關係
  3. 沒有 CRC，因為 TCP/IP 已經有檢查機制了
    • 所以常常會見到的是用 TCP 而不是 UDP，因為 TCP 有可靠傳輸的機制，UDP 沒有。

MBAP Header (Modbus Application Protocol Header)：

MBAP Header 長這樣：

  • Transaction Identifier：交易識別碼，2 byte，用來識別請求與回應的對應關係
  • Protocol Identifier：協定識別碼，2 byte，固定為 0x000
  • Length：長度，2 byte，表示後面資料的長度
  • Unit Identifier：單位識別碼，1 byte，用來識別設備，通常用於 Modbus TCP to Modbus RTU 的橋接器
Transaction Identifier Protocol Identifier Length Unit Identifier
2 Bytes 2 Bytes 2 Bytes 1 Byte

其中 Transaction Identifier 用來辨識是哪個請求的對應回應。

甚麼是 BMC ?

BMC (Baseboard Management Controller) 是一種嵌入式控制器，通常用於伺服器和高階工作站中，用來監控和管理硬體設備。BMC 提供了遠程管理功能，使系統管理員可以在不直接接觸伺服器的情況下進行操作，例如開機、關機、重啟、監控硬體狀態等。

工業電腦/伺服器中，其實不適只會有一個 CPU，通常會有兩個 CPU，一個是主要的 CPU，負責運行作業系統和應用程式，另一個是 BMC CPU，負責監控和管理硬體設備。(你可以當作有不只一個作業系統來理解)

近期的趨勢除了這兩個 CPU 之外，還會有一個額外 CPU，用來做 WatchDog，監控 BMC CPU 是否正常運作，若 BMC CPU 異常，則 WatchDog CPU 會重置 BMC CPU。算是用來提高系統的可靠性。
